# ESP32-S3 standalone bring-up — milestone 3

For ESP32-P4 diagnostics and Ethernet setup, see the [P4 bring-up guide](../../docs/ESP_IDF_P4_BRINGUP.md). Both targets use this project. For the M5Stack U213 Ethernet image, see the [U213 bring-up guide](../../docs/ESP_IDF_U213_BRINGUP.md). For the OTA profile, see the [U213 OTA guide](../../docs/ESP_IDF_U213_OTA.md).

This separate native ESP-IDF application is ready to build and flash to a
**standalone ESP32-S3 development board with every external header disconnected**.
Only the board and a USB data cable are needed. Do not connect the Buddy,
Driver boards, motors, RTC or harness. The working T-Display stays untouched.

It uses UART0 at 115200 through the board's **USB-to-UART** connector. It does
not start Chainlink GPIO/SPI2, Wi-Fi, PSRAM probing, NVS, filesystem or OTA. No
clock/latch/OE pulses are generated by the application. Proposed GPIO10..13
are not configured; UART0's normal GPIO43/44 and the boot flash-memory bus are
separate. ROM/SDK/board circuitry can still affect physical levels, so this is
not permission to connect external equipment.

## 1. Get and build the standalone image

Use ESP-IDF **v5.5.6**, commit `880a203ae603d08a94d06aa01e0d6761958e5e9e`.
On Void Linux install Espressif's Linux prerequisites (Git, Python, host C/C++
compiler, CMake, Ninja and required system libraries) using your normal package
manager. Then:

```sh
# SDK outside the checkout, once:
git clone --branch v5.5.6 --depth 1 --recursive --shallow-submodules \
  https://github.com/espressif/esp-idf.git "$HOME/esp/esp-idf-v5.5.6"
cd "$HOME/esp/esp-idf-v5.5.6"
./install.sh esp32,esp32s3
. ./export.sh

cd "$HOME/Projects/splitflap"
git fetch origin
git switch feature/esp-idf-s3-bringup
cd firmware/esp-idf-bringup
idf.py -B build-s3-bringup set-target esp32s3
idf.py -B build-s3-bringup build
idf.py -B build-s3-bringup size
python tests/check_isolation.py build-s3-bringup
```

If your checkout only fetches one branch, use
`git fetch origin refs/heads/feature/esp-idf-s3-bringup:refs/remotes/origin/feature/esp-idf-s3-bringup`
first. Keep local work committed/stashed before switching. No PR merge is needed.

Generated configuration lives in `build-s3-bringup/sdkconfig`. The image uses a
small **2 MiB header, DIO/40 MHz** and internal RAM only; no N8R8/N16R8 assumption.
These are boot-image settings, not detected memory specifications. The factory
application is at `0x10000` with a 1 MiB slot; S3 bootloader is at `0x0`, partition
table at `0x8000`. The diagnostic never initializes/writes NVS or FFat. Flashing
still overwrites bootloader/partition/application sectors, so do not use it on
the working controller or assume existing firmware/data will be preserved.

There is no universal flash-mode image for every unconfirmed S3 module. DIO/40 MHz
is the conservative initial SPI-flash profile, not a guarantee for an OPI-flash
module or unusual board. The preflight below identifies the chip/flash without
requiring a known capacity beforehand. If identification or boot shows a flash
mode/voltage incompatibility, stop and identify the exact module; do not guess
timing, voltage or eFuse settings. PSRAM is deliberately disabled, irrespective
of how much is fitted, so unknown PSRAM cannot block this application's startup.

## 2. Identify the correct Linux serial port

With no board plugged in, inspect the current list. Connect **one** data cable to
the connector labelled UART/USB-UART, then repeat:

```sh
ls -l /dev/serial/by-id/
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

Use the new stable `/dev/serial/by-id/...` path. Do not assume ttyUSB0/ttyACM0,
USB bridge vendor or that the two USB-C ports are interchangeable. USB-UART
usually creates a bridge-named port; the native USB port can create a different
device and is not this application's console. If there is no by-id link, match
the plug/unplug event using `dmesg --follow` (permissions may require sudo), then
use that verified `/dev/tty...` path. Exit the log viewer with Ctrl-C.

```sh
# Replace this illustrative path with the exact observed link:
export SPLITFLAP_PORT=/dev/serial/by-id/REPLACE_WITH_YOUR_UART_BRIDGE
readlink -f "$SPLITFLAP_PORT"
ls -l "$SPLITFLAP_PORT"
```

If access is denied, inspect the resolved device's group and your groups (`id`);
join the distro's serial-device group (often dialout or uucp) and log out/in.
Avoid world-writable device permissions. Close other monitors/programs using
the port. A charge-only cable will not enumerate a serial interface.

## 3. Read-only preflight and optional private backup

In the exported IDF environment, from `firmware/esp-idf-bringup`:

```sh
python -m esptool --chip esp32s3 --port "$SPLITFLAP_PORT" --baud 115200 chip_id
python -m esptool --chip esp32s3 --port "$SPLITFLAP_PORT" --baud 115200 flash_id
```

These are esptool **4.13.0** command spellings supplied by this SDK. They may
reset the dev board into ROM download mode, but do not erase/program flash.
Confirm an ESP32-S3, successful flash detection and at least 2 MiB before using
this image. Keep the output for diagnosing any boot mismatch. Do not infer PSRAM
from flash size. An unsupported ID, security-protection error or inconsistent
result is a reason to stop, not use `--force`.

If existing contents matter, back up the standalone dev board before overwriting:

```sh
mkdir -p "$HOME/splitflap-s3-backup"
python -m esptool --chip esp32s3 --port "$SPLITFLAP_PORT" --baud 115200 \
  read_flash 0 ALL "$HOME/splitflap-s3-backup/original.bin"
```

`ALL` detects the capacity; no guessed backup length is needed. Keep backups
outside Git and private because old firmware/data may contain credentials. Do
not upload a flash dump here. This task does not alter eFuses or security keys.

## 4. Flash and monitor (owner-run commands)

```sh
idf.py -B build-s3-bringup -p "$SPLITFLAP_PORT" -b 115200 flash
idf.py -B build-s3-bringup -p "$SPLITFLAP_PORT" monitor
```

The `flash` command programs the selected board; `monitor` opens its serial port.
The worker has run neither. Preflight also accesses/resets the device as described above.
Use IDF-generated offsets/arguments instead of guessing addresses or flashing
the application `.bin` alone. Monitor baud is 115200. Expect an initial info
report followed by `s3-bringup>`. Press Enter, then `help` or `info`. Exit IDF
Monitor with **Ctrl-]** to release the port before any subsequent flashing.

| Console command | Effect |
| --- | --- |
| `help` | IDF's registered command list/help |
| `info` | Chip/revision, physical flash and JEDEC status, PSRAM package hint, heap, reset/build/time and GPIO/SPI safety report |
| `pins` | Display informational assignments and reserved/duplicate conflicts; never configure a pin |
| `spi` | Report Chainlink SPI2 not linked/not initialized, zero transfers; no activation path |
| `time` | Show UTC, source, manual-provisioning status and explicit `EAP_TLS_authorized=no` |
| `time set YYYY-MM-DDTHH:MM:SSZ` | Set development UTC in RAM; strict UTC calendar validation, 1970..2099, no offsets/fractions/leap seconds |
| `reboot` | Restart; manual provisioning provenance is not persisted |

For current UTC, run `date -u +'%Y-%m-%dT%H:%M:%SZ'` in a separate Linux terminal,
then copy the value into `time set ...` at the device prompt. Invalid commands
(including `spi init`, `pins enable` or malformed dates) have no activation path.
Console history has eight entries in RAM only, with no filesystem history file.

## 5. Interpret `info` without guessing memory configuration

- `chip=ESP32-S3` and silicon revision come from `esp_chip_info`; these do not
  identify the PCB revision or a module's N/R suffix.
- **`flash_physical_bytes` with `status=ESP_OK`** uses
  `esp_flash_get_physical_size`. Divide by 1048576 for MiB. In contrast,
  `flash_image_access_limit_bytes` may remain 2097152 because that is the image
  envelope. The configured header is not a physical-capacity measurement.
  Detection is JEDEC/driver based; errors are reported, not replaced with a guess.
- `factory_hint_bytes` comes from read-only S3 package eFuse capacity codes.
  Codes 1/2/3/4 correspond to 8/2/16/4 MiB respectively, following Espressif's
  pinned esptool mapping. A positive hint indicates factory-marked embedded
  PSRAM; it is **not** an initialization, bus-mode, voltage or functional test.
- **`initialized_bytes=0` is expected in this first image.** PSRAM is not probed,
  so usable PSRAM heap is zero even if the package hint indicates 8 MiB. Code0,
  an unknown code or a read error means presence/capacity is unresolved; separately
  fitted module/board PSRAM is not ruled out. Do not label it absent or try both
  PSRAM bus modes. Paste the info and module marking first; a later matched
  configuration can initialize RAM and report its usable size/failure safely.
- Heap totals/free/largest-block values describe runtime allocator availability,
  not a measurement of all physical internal SRAM or a memory stress test.

The firmware's `info` report prints no MAC, unique flash serial, credentials or
key material (external esptool preflight output can include a MAC). Paste the
complete `info` block, `time` output and any boot errors into ChatGPT. Include the
board/module marking separately when available; `info` cannot discover a PCB's
exact header routing.

## Clock provenance

A UTC timestamp is generated on the first build and when application/configuration
inputs change, using an explicit UTC host clock. A no-change build, `size` or
`monitor` does not regenerate it or change the flashed image's matching ELF.
`SOURCE_DATE_EPOCH` can supply a reproducible timestamp; `info` identifies that
source. At startup the timestamp initializes the system clock only if there is
no plausible later clock in the supported range. A retained later value is
labelled unverified. Both are approximate/untrusted. Clock-set errors leave the
state unprovisioned and are printed.

A successful manual `time set` marks this boot as serial-provisioned development
time. It does **not** authorize strict EAP-TLS or create an authenticated time
source. No Wi-Fi/EAP client is linked, and `EAP_TLS_authorized` stays `no` for
every state. After reboot, provenance is forgotten even if RTC hardware retains
a plausible time: the next boot reports retained/unverified or build approximate.
No NVS timestamp, RTC chip, NTP or certificate/date bypass is used.

## If it does not boot or the prompt is missing

1. Keep all headers disconnected. Confirm one UART USB data cable, correct port,
   115200 monitor baud and no other process holding it. Press the labelled Reset/EN
   button and capture the ROM/boot log; an idle prompt may need Enter.
2. To recover ROM download mode, use the board's labelled buttons: hold **BOOT**,
   press/release **RESET/EN**, then release BOOT. Close the monitor and retry
   `flash_id` over USB-UART. If the button arrangement differs, consult that exact
   board's documentation; do not jumper unknown contacts.
3. Retry the IDF `flash` command at 115200 and then monitor. A board with native
   USB app issues is often still reachable through its separate USB-UART bridge.
   Firmware cannot repair a missing bridge driver, charge-only cable or bad power.
4. For invalid headers, flash-mode errors, unsupported memory/security settings
   or a reboot loop before `app_main`, stop and share the boot/preflight text.
   This firmware cannot print a memory-init error that occurs before it boots.
   Do not randomly enable PSRAM, change memory voltage/eFuses, use `--force`, or
   perform a blanket erase. A successful compilation does not prove board boot.
5. Restore a verified matching backup only in a separately reviewed recovery
   procedure, respecting the device's security state. Keep the working original
   T-Display/controller completely out of this process.

## Owner checklist and verification boundary

- [ ] Standalone S3 only; every external header disconnected; one UART USB cable.
- [ ] Identify the Linux port and complete read-only chip/flash preflight.
- [ ] Preserve any needed existing dev-board contents before flashing.
- [ ] Build/flash this separate project, not `firmware/esp-idf` or PlatformIO.
- [ ] Run `help`, `info`, `pins`, `spi`, `time`, manual `time set`, then `time`.
- [ ] Run `reboot`; confirm reset reason/provenance and that no external activity
  or PSRAM initialization was requested.
- [ ] Paste `info` and observed results for the next milestone. No harness or
  motor testing is part of this checklist.

Local/CI builds, host test results and offline command/image checks are recorded
in [milestone 3 verification](../../docs/ESP_IDF_S3_BRINGUP_VERIFICATION.md).
Actual UART interaction, reset behavior, physical memory detection and boot
compatibility remain for the owner to observe; they were not simulated as passes.
